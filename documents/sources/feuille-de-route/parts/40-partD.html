Partie D

ESB — bus de services d’entreprise

Un ESB est un intermédiaire placé entre PleasantStay et les systèmes extérieurs : il reçoit les événements métier, les achemine vers les bons destinataires, les signe, réessaie en cas d’échec et garde une trace de chaque échange. PleasantStay ne connaît ainsi qu’un seul format interne ; chaque partenaire est branché sans toucher aux modules métier.

Dans quel cadre l’utiliser… et dans quel cadre ne pas l’utiliser

✓ Utiliser l’ESB pour les échanges avec l’extérieur
  • Canaux de vente : Booking.com, Expedia, Airbnb, Agoda, directement ou via un channel manager (SiteMinder, Channex) — disponibilités et tarifs sortants, réservations entrantes (n° 10).
  • Paiement : CinetPay, Orange Money, MTN MoMo, Moov, Wave, Stripe — confirmations de paiement entrantes signées (n° 9).
  • Comptabilité externe : Sage, Odoo comptable, cabinet d’expertise — écritures validées (accounting.entry.posted).
  • Décisionnel : entrepôt de données, Power BI, Metabase — flux de réservations, ventes et stocks.
  • Serrures et clés : Salto, ASSA ABLOY Vostio — clé émise à l’arrivée, révoquée au départ (n° 12).
  • Centrale de réservation d’un groupe multi-établissements.
  • Autorités : transmission des fiches de police (n° 23).
  • Messagerie : fournisseurs SMS et WhatsApp, routage des campagnes (n° 13).
  • E-réputation : import des avis Google et OTA (n° 29).
✗ Ne pas l’utiliser pour la communication interne
  • Back-office, site public et application mobile ↔ API : appels REST directs, avec les gardes d’authentification existantes.
  • Entre applications du même backend (facture → comptabilité, départ → stock, départ → fidélité) : bus d’événements interne DomainEventPublisher, déjà en place, dans le même processus.
  • Temps réel du tableau de bord (n° 19) : flux SSE direct.
  • Calculs synchrones (disponibilité, devis) : appels de service ; l’ESB est asynchrone par nature.
  • Règle simple : si l’échange reste à l’intérieur de PleasantStay, pas d’ESB.

Architecture cible

Le principe clé est la boîte d’envoi (outbox) : quand un événement est publié, l’ESB insère une ligne par destinataire dans outbox_messages, sans jamais appeler le réseau pendant la requête métier. Le dispatcher lit ensuite les lignes dues, les réserve par un bail (deux instances ne livrent jamais le même message), livre, puis marque « livré », « à réessayer » ou « mort ». L’index unique (event_id, endpoint_id) rend l’ajout idempotent. Pour une garantie totale (événement écrit si et seulement si l’écriture métier réussit), l’étape suivante consiste à insérer la ligne outbox dans la même transaction MongoDB que l’écriture, ce qui suppose un replica set (n° 25).

RègleComportement réalisé
Réponse attendue2xx = livré ; 410 = point de terminaison désactivé ; toute autre réponse ou délai dépassé = nouvelle tentative.
ReprisesDélai exponentiel 30 s × 2n avec 20 % d’aléa, plafonné à 6 h ; 8 tentatives par défaut puis statut « mort », relançable depuis POST /integration/outbox/:id/retry.
Désactivation automatiqueAprès 50 échecs consécutifs, le point de terminaison est désactivé pour protéger le dispatcher.
SSRFHTTPS obligatoire en production ; refus des identifiants dans l’URL et des adresses privées, de bouclage, lien-local et de métadonnées cloud, vérifiées à l’enregistrement et à chaque livraison (résolution DNS) ; dérogation locale par INTEGRATION_ALLOW_PRIVATE_URLS=true.
SecretsChiffrés AES-256-GCM avec INTEGRATION_ENCRYPTION_KEY ; jamais relus par l’API (indice masqué), nouveau secret affiché une seule fois à la rotation.
EntrantClé d’URL aléatoire par source, signature v1 ou en-tête HMAC configurable, tolérance 300 s, dédoublonnage par identifiant d’événement du fournisseur, réponse 202.

src/integration-bus/brokers/amqp-broker.adapter.ts (à créer)
@Injectable()
export class AmqpBrokerAdapter implements MessageBrokerAdapter, OnModuleDestroy {
  private channel?: ConfirmChannel;
  private async ch() {
    if (!this.channel) {
      const conn = await amqp.connect(process.env.AMQP_URL!);
      this.channel = await conn.createConfirmChannel();
      await this.channel.assertExchange('pleasantstay.events', 'topic', { durable: true });
    }
    return this.channel;
  }
  async publish(routingKey: string, envelope: OutboundEnvelope, o?: { messageId?: string }) {
    const ch = await this.ch();
    ch.publish('pleasantstay.events', routingKey, Buffer.from(JSON.stringify(envelope)),
      { persistent: true, messageId: o?.messageId, contentType: 'application/json' });
    await ch.waitForConfirms();     // sinon : erreur → message retenté
  }
  async onModuleDestroy() { await this.channel?.close(); }
}
// integration-bus.module.ts : { provide: MESSAGE_BROKER_ADAPTER, useClass: AmqpBrokerAdapter }
