Partie E

Socle ERP modulable

Réalisé et vérifié en novembre 2026 : 141 suites et 1682 tests unitaires, plus un test de bout en bout de 14 contrôles sur une base réelle. Ces éléments ne font pas partie des 30 fonctionnalités manquantes. Ils transforment PleasantStay en plateforme d’applications activables par organisation, à la manière d’Odoo.

Toutes les applications sont enregistrées dans src/app.module.ts et reposent sur src/platform/, module global : chaque contrôleur porte @RequiresApp('<clé>'), les applications communiquent uniquement par événements, et toutes les pièces sont numérotées sans trou par établissement et par année. Côté back-office (project-manager-hotles-backoffice), 28 pages de ressources src/app/admin/<clé>/page.tsx sont déclarées dans src/lib/erp-resources.ts ; src/lib/workspace.tsx mémorise l’organisation et l’établissement courants ; src/components/ui/ResourcePage.tsx gère les actions de workflow par ligne et l’éditeur de lignes ; src/components/layouts/Sidebar.tsx affiche une section par application installée.

Magasin d’applications avec dépendances Réalisé

21 applications au catalogue (11 existantes regroupées, 10 nouvelles). Installer une application installe d’abord ses dépendances (ex. Achats → Stock) ; une désinstallation est refusée tant qu’une application dépendante est installée ; la garde globale renvoie 403 si l’organisation n’a pas installé l’application.

  • Backend : src/platform/apps/app-catalog.ts, apps.service.ts, apps.controller.ts (GET /apps, POST /apps/:key/install, /uninstall), app-installed.guard.ts, requires-app.decorator.ts, organization-app.entity.ts
  • Back-office : src/app/admin/apps/page.tsx (magasin d’applications), src/components/layouts/Sidebar.tsx
Événements métier, portée et numérotation Réalisé

Catalogue de 38 événements, publication qui n’interrompt jamais l’opération d’origine ; réservations, factures, paiements et point de vente publient désormais leurs événements. Résolution établissement → organisation mise en cache ; compteurs atomiques sans trou.

  • Backend : src/platform/events/domain-events.ts, domain-event.publisher.ts, src/platform/tenancy/tenant-scope.service.ts, src/platform/sequences/sequence.service.ts, src/platform/platform.module.ts ; dépendances @nestjs/event-emitter, @nestjs/schedule
Comptabilité SYSCOHADA Réalisé

Plan SYSCOHADA de 51 comptes adapté à l’hôtellerie (dont 552 « monnaie électronique » pour le mobile money), journaux VTE, ACH, CAI, BNQ, MOB et OD, écritures en partie double contrôlées, date de verrouillage, extourne. Comptabilisation automatique des factures, paiements, remboursements, ventes et annulations du point de vente, factures fournisseurs ; balance, grand livre, compte de résultat, bilan, balance âgée clients.

  • Backend : src/accounting/ (domain/syscohada-chart.ts, domain/posting-rules.ts, domain/accounting.logic.ts, listeners/accounting-auto-posting.listener.ts)
  • Back-office : src/app/admin/accounting-accounts/, accounting-journals/, accounting-entries/, accounting-reports/page.tsx
Stock Réalisé

Articles (minibar, restauration, produits d’accueil, entretien, linge, pièces), emplacements, mouvements validés, quantités par emplacement sans stock négatif, coût moyen pondéré, inventaires physiques, valorisation. Consommation automatique des kits d’accueil à chaque départ ; alerte de seuil bas.

  • Backend : src/inventory/ (product, stock-location, stock-move, stock-quant, inventory-count ; listeners/checkout-consumption.listener.ts)
  • Back-office : src/app/admin/products/, stock-locations/, stock-moves/, inventory-counts/
Achats Réalisé

Fournisseurs, bons de commande avec seuil d’approbation, réceptions partielles qui alimentent le stock, factures fournisseurs comptabilisées automatiquement. Réapprovisionnement intelligent : une alerte de stock bas ajoute la quantité manquante au brouillon de commande du fournisseur préféré.

  • Backend : src/purchase/
  • Back-office : src/app/admin/vendors/, purchase-orders/, vendor-bills/
Ressources humaines Réalisé

Construite sur le personnel existant (src/staff/) : départements, contrats (CDI, CDD, intérim, stage, journalier) avec expiration automatique, types de congés, allocations, demandes avec soldes et circuit de validation, planning des équipes avec détection des chevauchements (y compris de nuit), pointage. La paie (n° 27) s’appuiera sur cette application.

  • Backend : src/hr/
  • Back-office : src/app/admin/hr-departments/, hr-contracts/, hr-leave-types/, hr-leave-allocations/, hr-leaves/, hr-shifts/, hr-attendance/
CRM Réalisé

Étapes de pipeline paramétrables, comptes entreprises (remise négociée, plafond de crédit), pistes et opportunités par segment (groupe, séminaire, mariage, contrat entreprise, long séjour), nuitées calculées, chiffre d’affaires pondéré et prévision par mois d’arrivée.

  • Backend : src/crm/
  • Back-office : src/app/admin/crm-pipeline/page.tsx (colonnes par étape), crm-leads/, crm-stages/, crm-corporate-accounts/
Fidélité Réalisé

Programmes par établissement ou par organisation, paliers avec multiplicateurs, grand livre des points idempotent, gain automatique au départ et au point de vente, utilisation contrôlée (solde, minimum), ajustements motivés, expiration planifiée ; synchronisation avec les champs fidélité de la fiche client.

  • Backend : src/loyalty/
  • Back-office : src/app/admin/loyalty-programs/, loyalty-accounts/
Fil d’activité (« chatter ») Réalisé

Sur chaque fiche déclarée au registre : notes, abonnés, activités planifiées (appel, réunion, tâche) avec échéance, « Mes activités », historique automatique alimenté par les événements métier (« Réservation confirmée », « Facture payée »…).

  • Backend : src/records/ (record-registry.ts), src/activity/ (activity.service.ts, activity-tracking.listener.ts, activity-due.scheduler.ts)
  • Back-office : src/app/admin/my-activities/page.tsx ; fil d’activité sur les fiches : à faire (n° 18)
Studio : champs personnalisés Réalisé

Chaque organisation ajoute ses propres champs (texte, nombre, date, liste, montant, e-mail…) aux fiches, sans développement ; valeurs validées selon leur définition et stockées à part des documents métier.

  • Backend : src/studio/ (custom-field.validator.ts, schemas/custom-field.entity.ts, schemas/custom-field-value.entity.ts)
  • Back-office : src/app/admin/studio-fields/ (définitions) ; saisie des valeurs sur les fiches : à faire (n° 18)
Automatisations Réalisé

Règles « quand… si… alors… » sur les 38 événements : conditions combinables, actions « créer une activité », « écrire une note », « notifier », « publier sur l’ESB » ; essai à blanc, journal d’exécution, protection contre les boucles.

  • Backend : src/automation/
  • Back-office : src/app/admin/automation-rules/, automation-runs/ ; éditeur visuel : à faire (n° 18)
Bus d’intégration (ESB) Réalisé

Boîte d’envoi, dispatcher avec reprises et messages morts, webhooks signés HMAC, garde SSRF, secrets chiffrés AES-256-GCM, entrée signée POST /api/integration/inbound/:endpointKey (corps brut activé dans src/main.ts), adaptateur de courtier prêt pour RabbitMQ (détails en partie D).

  • Backend : src/integration-bus/ (utils/signature.ts, utils/ssrf-guard.ts, utils/backoff.ts, brokers/message-broker.adapter.ts, services/endpoint-delivery.service.ts)
  • Back-office : src/app/admin/integration-endpoints/, integration-inbound-sources/, integration-outbox/
Base de données et vérification Réalisé

npm run seed prépare une base complète et peut être relancé sans risque : 89 collections et leurs index, 8 rôles système, un super-administrateur, un hôtel de démonstration (3 types de chambre, 12 chambres), les 21 applications installées et configurées (plan comptable, emplacements de stock, 4 articles, un fournisseur, étapes CRM, 4 types de congés, programme de fidélité).

npm run test:erp-smoke : 14 contrôles sur 14 réussis — séjour → fil d’activité, note d’automatisation, points de fidélité et consommation du kit d’accueil ; facture → écriture VTE ; paiement mobile money → MOB ; commande → réception → facture fournisseur → ACH et stock ; balance équilibrée ; webhooks ESB signés et vérifiés ; désinstallation → 403 ; dépendance → 409.

  • Backend : src/scripts/seed.ts, src/scripts/seed-erp.ts, test/erp-smoke.mjs
  • Exploitation : limite de fichiers ouverts de MongoDB portée à 64 000 dans les deux docker-compose.yml (sinon arrêt WiredTiger EMFILE vers 90 collections)
Liens avec le reste du document
  • La comptabilité automatique n’est juste que si les factures le sont : les fiches n° 2, 3 et 4 (prix calculé, folio, facture légale) sont prioritaires.
  • Le back-office n’affiche pas encore les champs personnalisés et le fil d’activité sur les fiches, ni les rapports Stock et Achats, le planning RH, les réglages RH / Achats / Comptabilité et l’éditeur visuel d’automatisations : ces écrans sont repris dans la fiche n° 18.

  • Les automatisations peuvent publier vers l’ESB (partie D) : « quand une facture est payée, si le client est une entreprise, alors envoyer l’écriture au cabinet comptable ».
